**Контекст.** Мы делаем вход в веб-приложение. Пользователь вводит email и пароль, фронтенд отправляет их на `/api/login`, а сервер возвращает JWT. JWT — это строка-пропуск: её прикладывают к каждому следующему запросу, чтобы сервер знал, кто вы. Пропуск действует 1 час. Код я пока не писал, потому что сначала нужно решить, **где фронтенд хранит этот пропуск**.

Решение важно из-за одной особенности проекта. На каждой странице работают три чужих скрипта: чат-виджет, A/B-тесты и аналитика. Так написано в комментарии в `web/src/widgets.ts`, а кода, который их подключает, в репозитории нет. Эти скрипты выполняются с теми же правами, что и наш код. Если какой-то из них взломают, он сможет прочитать всё, что доступно нашему JavaScript.

**Что известно:** API на `api.example.com`, сайт на `app.example.com`. Мобильное приложение тоже ходит на `/api/login` и ждёт пропуск в теле ответа, это нельзя сломать. Кода сервера в репозитории нет, только README.

**Пример: взломали чат-виджет**

| | Что может злоумышленник |
|---|---|
| 1. Cookie, недоступная JS | Отправлять запросы от имени пользователя, пока у того открыта вкладка. Унести сам пропуск не может |
| 2. Переменная в памяти | Перехватить ответ `/api/login` при входе и унести пропуск. Это сложнее, чем в варианте 3, но возможно |
| 3. `localStorage` | Одной строкой прочитать пропуск, отправить к себе и целый час входить под пользователем откуда угодно |

**Варианты**

1. **Cookie с флагом HttpOnly.** Сервер сам кладёт пропуск в cookie, которую браузер прикладывает к запросам, а JavaScript её не видит.
   - Плюсы: самый надёжный из трёх, пропуск нельзя украсть скриптом.
   - Плюсы: пользователь остаётся залогиненным после перезагрузки страницы.
   - Минусы: нужно менять сервер (выставлять cookie, настраивать CORS, то есть разрешение браузеру ходить с сайта на API с cookie).
   - Минусы: нужна защита от CSRF (когда чужой сайт заставляет браузер отправить запрос с вашей cookie). Это ещё немного работы на сервере.
2. **Только в памяти страницы.**
   - Плюсы: сервер не трогаем.
   - Минусы: после перезагрузки страницы пользователя выкидывает. Чтобы это исправить, всё равно нужна правка сервера.
   - Минусы: от взломанного виджета защищает лишь частично (см. таблицу).
3. **`localStorage`** (постоянное хранилище браузера).
   - Плюсы: проще и быстрее всего, сервер не трогаем.
   - Минусы: любой из трёх чужих скриптов читает пропуск напрямую.

**Рекомендация:** вариант 1, но не окончательно. Он единственный, где пропуск нельзя унести. Сильнее всего против него то, что придётся менять сервер. Если сервер менять нельзя, разумный компромисс — вариант 2. Мою рекомендацию может изменить одно: можно ли править сервер. Из репозитория этого не видно.

**Вопрос:** где храним пропуск: 1 (cookie, нужна правка сервера), 2 (в памяти) или 3 (`localStorage`)? Если выбираете 1, можно ли менять сервер?

Отдельный мелкий вопрос: фронтенд шлёт запрос на `/api/login` без домена, а API живёт на `api.example.com`. Значит, есть прокси, который пересылает такие запросы, или адрес надо поправить. Как у вас настроено?
